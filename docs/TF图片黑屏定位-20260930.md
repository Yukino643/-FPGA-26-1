# TF 图片黑屏定位（2026-09-30）

> 本文记录 19:17:55 的上一轮修复。板上验证仍无图，且随后已完成 H: 卡布局检查；当前诊断版和操作依据见 [TF诊断版-20260930.md](TF诊断版-20260930.md)。文中的“卡未接电脑”属于当时的历史状态。

## 现象与结论

Julian 已在板上下载前次 SDHC 修复版本，HDMI 广告界面正常，但数码管最终显示 1，无 TF 图片。

数码管连接 `bmp_read_g.state_code`，1 对应 `ST_IDLE`。扫描未找到图片、扫描超时和装载头失败都会回到该状态，因此 1 不是读卡成功或失败的独立诊断码。

本轮从安路 `7_lab_ex_2026_nosoft/*/lab_ex4_tf` 官方例程和素材对照，确认并复现当前泛化 BMP 模块的两处错误。

## 官方例程对照及根因

| 项目 | 官方实现 | 修复前当前实现 | 直接证据 |
|---|---|---|---|
| BMP 头字段采样 | `rd_cnt` 继续计数，offset 33 后不命中头字段 case | `hdr_cnt` 饱和在 33，后续所有字节持续改写 compression 的最高字节 | 官方三图真实 compression=0，但 byte[511]=FF，首扇区结束时被改为 FF000000，扫描全部拒绝 |
| RGB 拼包 | `bmp_data_valid` 包含 `sd_sec_read_data_valid` | `byte_is_pixel` 只判断字节位置，拼包每拍推进 | 每字节插入 7 个空拍时，5×2 图片应输出 10 像素，实际输出 80，出现重复字节和颜色错位 |
| TF 引脚 | CLK=A14、MISO=B14、MOSI=A13、CS=A12 | 与官方一致 | 两份 pin.adc 对照 |
| SD 初始化 | 官方缺少 CMD58 容量识别，就绪置位过早 | 前轮已修复，当前使用 CMD58/OCR 与 SDHC/SDSC 寻址 | 本轮新增 SPI 引脚模型，验证 FSM+command+SPI 完整链，而非仅 mock command ACK |

三张官方素材的共同头部：文件大小 921654，像素偏移 54，DIB=40，宽 640，高 480，planes=1，bpp=24，compression=0。它们本身满足当前格式要求。

## 修复

1. 将头部计数器饱和哨兵改为 34，偏移 34 后不再改写任何头字段。
2. 像素拼包只在 `sd_sec_read_data_valid` 时前进，空拍保持 byte_idx；写使能默认撤销，收到第三个有效字节时仅输出一拍。
3. 官方图首扇区夹具纳入回归，覆盖扫描和装载头两条路径。
4. 原像素回归新增 BYTE_GAP 参数，正式门使用每字节 31 空拍，同时保留连续供数回归。
5. SPI 引脚链回归覆盖 SDHC 与支持 CMD8 的 SDSC，检查 CMD58、CMD16、CMD17 地址换算、两次完整 512 字节扇区及 CRC 字节隔离。模型未覆盖所有 SD 卡异常响应或真实信号完整性。

## 卡布局边界与板上步骤

当前扫描 LBA 0～131071（前 64 MiB），目标最多 8 张。找到 8 张或范围扫描完才启动首图装载。只有 3 张时需扫完范围，不应仅据等待时间判断成败。代码不解析 FAT32 目录及簇链：图片头在范围外无法发现；文件碎片化可能使顺序读扇区无法还原图片；删除的旧图也可能被扫描。

当前电脑没有检测到这张 TF 卡，因此未确认卡内三文件与官方素材是否完全一致、物理起始 LBA 是否在扫描范围、簇链是否连续。这些不能冒充已验证。

1. 使用本轮重建的 `td_prj/av_media_Runs/phy_1/av_media.bit` 临时下载；工程入口仍为 `td_prj/av_media.al`。
2. 下载前插好卡；主广告画面接 HDMI_B，监视台接 HDMI_A。
3. 观察扫描状态 2、装载状态 3/4，以及监视台图片数、源图尺寸和主屏图像。状态跳变很快，不要求肉眼一定捕捉到。图片数在扫描结束后才更新，扫描期间显示 0 不能单独说明未发现图片。
4. 若仍无图，将卡插入读卡器再做只读布局检查，不能先推断是卡品牌问题。
5. 不要直接运行官方/当前 `sync_to_sd.py`：它会改写旧图头并清空卡文件，且不能保证 FAT 分配的物理连续性。
