# HDMI-B偶发白色颗粒：刷新缺陷修复

用户反馈：切到新图后偶发轻微白色颗粒，有时持续到再次切换；只发现HDMI-B异常。应急模式和播放按键已由用户确认通过。

## 已确认的缺陷

`rtl/mem/include/global_def.v`原来定义：

```verilog
`define SDR_CLK_PERIOD 1000000000/125000000
`define SELF_REFRESH_INTERVAL 64000000/`SDR_CLK_PERIOD/2**(`ROW_WIDTH)
```

宏是文本替换。第二个表达式展开为`64000000/1000000000/125000000/2**11`，左结合整数除法得到0。

实际IP文件`sdr_init_ref.enc.v`的可读前缀中，`init_cnt`等于该终值便归零；周期为0使计数停在0。`ref_req`又要求计数等于周期减10，因而没有周期刷新请求。顶层`App_ref_req`固定为0，没有其他显式请求补偿。

当前系统会预取下一张图片：后台页写完后等待用户按键，等待时间可能远大于刷新窗口。因此“整帧写完再发布”不能代替刷新保护；后台页即使曾经完整写入，驻留期间仍有数据保持风险。这个路径与偶发切到一张有颗粒的新图相符。

老师完赛工程的`project_code/dependencies/lesson36_build/src/sdram/enc_file/global_def.v`已用括号修正同类问题；其中40MHz属于老师工程，不能直接代替本工程125MHz。

## 修改范围

- 只修改配置头；不修改加密IP、不改变PLL、不降低720p、不改变菜单和按键。
- 时钟周期8ns。2048行的刷新预算为64ms；计数器包含归零拍，所以终值为3905，相邻请求3906拍，即31.248µs。
- 新测试提取当前IP第一个protected区之前的实际原文，验证计数与请求；ACK模拟1/140/268/660拍有限忙等待。
- 新测试覆盖超过64ms、重新复位/初始化、关闭自动刷新及显式请求。缓存依赖包含实际宏头，避免复用旧PASS。

## 证据与边界

修复前失败日志：`.trellis/tasks/10-17-image-sparkle-refresh/before-fix-refresh.log`，实测宏周期8ns、刷新终值0、周期请求0。

SDRAM理想数组不会因不刷新而丢数据，原有像素仿真因此漏掉此类问题。新测试证明实际可读刷新计时逻辑；没有仿真加密命令生成器、物理SDRAM保留时间或板上信号完整性。

缺少刷新与驻留像素受损相符，但软件检查不能证明本次颗粒只有这一个成因。应以本轮新bit验证；若仍复现，再继续检查源数据传输、存储读写裕量和输出链路。

## 板级复测

1. 使用本轮明确交付的新bit，同时连接双屏，确认应急、菜单及图片功能保持正常。
2. 循环切换至少50次，既测预取已完成后的单次切换，也测连续按键排队后的切换；分别停留2秒、10秒、60秒后再切到预取页，留意等待越久是否更容易出现颗粒。
3. 每张图静态停留至少1分钟；至少再保持一张图10分钟，检查颗粒是否逐渐出现。
4. 自动轮播运行30分钟，检查双屏、音频和波形。
5. 若复现，记录图片编号、颗粒固定还是游动、停留时间、再次切回同图是否恢复；保留失败结果，不判验收通过。
